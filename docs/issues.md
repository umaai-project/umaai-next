# 问题记录

记载复杂问题的解决过程与根因，避免重复踩坑。

## 2026-10-17

### 搜索根必须取在决策点

- **现象**：搜索内核的真实 rollout 测试在人头分配处越界 panic（`distribution` 长度为 0）。
- **排查**：`newgame` 的初始局面停在回合 0 的 `Begin` 阶段，人头分布要到 `Distribute` 阶段才生成；测试直接拿初始局面跑训练动作，等于在非法搜索根上做 rollout。
- **结论**：测试夹具用真实 `run_stage` 推进到 `Train` 阶段再取根（生产搜索的调用点、人头分布已完成），crate 内与跨 crate 端到端夹具同法。

### 桩 rollout 的分数口径必须只依赖动作身份

- **现象**：候选顺序不变性测试失败，同一动作在正序/逆序下均分差 6000。
- **排查**：桩分数用「候选下标 × 1000」当基线，逆序后同一动作的下标变了，分数随之改变——失败是夹具造成的假信号，不是内核问题。
- **结论**：桩函数改由动作身份映射基数，候选下标只用于下标相关断言（如按序取种子）。

### `cargo check` 漏检测试代码

- **现象**：`cargo check -p <crate>` 通过，但 `cargo test` 编译失败（测试模块内的错误）。
- **排查**：`cargo check` 默认只检查 lib / bin target，不含 `#[cfg(test)]` 与 `tests/` 目录。
- **结论**：本地门禁统一用 `cargo check --all-targets` / `cargo clippy --all-targets`（与 CI 一致），避免测试代码漏检到 test 阶段才暴露。

### lint 门禁在 P4 开工前就是红的

- **现象**：`cargo clippy --workspace --all-targets -- -D warnings`（CI 口径）失败，29 处 lint 告警分布在上一阶段代码里；另有 3 处 rustdoc 链接告警。
- **排查**：这批告警属历史欠账，与本次改动无关；CI 门禁自带了 `-D warnings`，说明此前提交前未按同一口径跑过本地门禁。
- **结论**：逐条判定语义等价后修复——整型夹取改 `clamp`；浮点夹取先确认输入不可能是 NaN（数值来自 JSON 整数）再改 `clamp`，因为 `f.min(b).max(a)` 与 `f.clamp(a, b)` 在 NaN 上结果不同（前者取边界，后者传播 NaN）；默认值后逐字段赋值改结构体字面量；纯下标循环改迭代器；可合并的嵌套 `if` 改 let-chain；仅「参数过多」一处保留并加 `allow` 与理由（热路径上聚成结构体会多一层间接）。文档链接告警按 rustdoc 规则改为可解析目标。
- **口径**：本地门禁与 CI 完全一致——`cargo fmt --all --check` + `cargo clippy --workspace --all-targets -- -D warnings` + `cargo test --workspace --release`，另加 `cargo doc --no-deps` 作为链接告警检查。

### 配置默认值只能有一份

- **现象**：旧仓同一参数在代码 serde 缺省与 `default_config.toml` 各有一套默认值，实测分歧（搜索次数、激进度上限、期望标准差、剧本与训练员默认值等），只能靠在测试里同时钉住两个源；用户覆盖层还有「段缺失把默认整段清空」的陷阱（默认出行顺序被覆盖层空值清成空表）。
- **根因**：结构体字段带 serde 缺省、文件里再写一份字面量，两份「默认」没有同步机制；覆盖层用「整段可选结构体」而非「字段可选」，因而无法区分「没写」与「显式给空」。
- **结论**：默认值只存在于数据根配置文件，Rust 侧不为同名字段提供缺省，缺字段即报错并指明字段；覆盖层与默认层同构、字段全可选，段缺失即整段沿用；配置与程序同版本发布，故未知键严格报错（对外帧协议另按宽容口径处理，两者不共用纪律）。

### 真实事件 ID 编码：不能按末位判段

- **现象**：从真机帧还原事件历史时，一条角色事件被算成了「支援卡连续事件第 1 段」。
- **排查**：线上事件 ID 形如 `8 + 归属(5 位) + 序号(3 位)`：归属首位 `3` 为支援卡（值 = 卡 ID）、首位 `0` 为角色 / 友人（值 = 角色 ID），序号是该对象的事件序号。真机样本完全吻合（卡 30137/30242/30289/30297/30304、角色 9001/9044），模拟表 `friend_events` 也是同法编码（角色 9050）。旧实现按 `id % 10` 判卡事件段——卡事件序号恰好是 1/2/3 时看着没错，但角色事件序号是三位数（如 `809001101` 是角色 9001 的第 101 号事件），末位为 1 就被误算进卡事件第 1 段。
- **结论**：先按归属判族，再用三位序号；卡事件按序号归到模拟表的段模板，角色 / 友人事件按真实 ID 入账（模拟表若收录同族事件，ID 天然相同，能对上即精确对齐）。真机帧上的可见差异：一组四条关键事件的段计数由 4 修正为 3 段 + 1 条角色事件。

### 事件成功/失败的建模口径待真实剧本校准

- **背景**：实机事件帧带「成功效果 / 失败效果」两支数值，而模拟事件表**没有「事件成功失败」这一维度**——剧情 / 卡 / 友人事件全是单支必定触发，只有系统事件的比赛结果类带概率。且真实事件 ID 与模拟表 ID 基本不重叠，不存在现成的「真实事件 → 模拟事件」映射。
- **现状（临时口径）**：帧事件按两支重建为待处理事件，两支按常量表的**通用默认成功率**分概率；只有一支带数值时该支必定触发；决策与结算共用同一份数据（同一对象）。事件数值缺失只跳过该事件并留下诊断，不牵连整帧。这一口径会同时影响事件决策的期望值与运气分基线，故不能算最终定论。
- **待调整**：通用默认成功率未必是该事件的真实成功率。等有真实剧本与真机数据后校准，可选方向：按事件类别 / ID 查更细的成功率表；或改成「决策看两支期望、结算以真实结果为准（由下一帧带回）」。调整时只需改事件重建那一处，决策与结算同源这一点不应破坏。
- **边界**：未来事件仍由模拟表 + 概率生成（不可知），只能靠「已发生事件的分族入账」对齐历史，无法消除时机与条件的偏差。

### 合成帧的卡组字段必须带突破等级

- **现象**：会话端到端首次运行即失败，报「校验失败 cardDB.json/3024: 未找到该 ID」。
- **排查**：协议 `cardId` 是「卡 ID × 10 + 突破等级」的合并值，解析侧由支援卡构造拆开取卡面与等级；测试合成帧时直接写了卡面 ID，被拆成「卡面 ID / 10」再去查表，必然查不到。
- **结论**：合成帧的卡组字段一律按合并值写出（旧仓导出方向同法）；真机帧本就是合并值，夹具可直接用。

## 2026-10-16

### 离线环境下的依赖添加

- **现象**：`cargo add serde_json` 退出 101，报 `rsproxy.cn:443 over proxy 127.0.0.1` 连接失败。
- **排查**：`cargo add` 需联网更新注册表索引；本地缓存中已有目标 crate 与锁文件解析结果。
- **结论**：加 `--offline` 即可走本地缓存完成添加。另需注意 `cargo add` 无 `--workspace` 标志（`--workspace` 会被当作依赖名），往 `[workspace.dependencies]` 登记需按 cargo 解析出的版本手工补一行，再把成员依赖改为 `workspace = true`。

### 核对依赖是否有新版的可行手段

- **现象**：`cargo info <pkg>` 退出 101，报 `crates-io is replaced with non-remote-registry source registry 'rsproxy-sparse'`。
- **排查**：该子命令只接受 crates-io 源，替换源下需显式 `--registry crates-io`（走直连）。
- **结论**：核对版本改用 `cargo update --dry-run --verbose`——它对「有更新但被版本要求挡住」的包打印 `Unchanged <pkg> vX (available: vY)`；未出现的包即为当前最新。

## 2026-10-15

### rand 依赖版本锚定（0.9.5）

- **现象**：`cargo add rand` 默认解析到 `0.10.3`；核心层接入 `rng.rs` 后 `use rand::RngCore` 编译失败。
- **排查**：rand 0.10 为破坏性改版——`RngCore` 改名 `Rng`（rand_core）且旧名标记 deprecated、扩展 trait `Rng` 改名 `RngExt`、`StdRng` 移除 `Clone`、`OsRng`→`SysRng`、`choose_multiple`→`sample` 等。生态已跟进（`rand_distr 0.6.0` 要求 `rand ^0.10`），故非「无法升级」。
- **结论**：核心层锚定 `rand 0.9.5`（0.9 线最新补丁，与旧仓解析口径一致），后续配套 `rand_distr 0.5.x`。理由：后续阶段要移植的是基于 0.9 API 的存量代码，升 0.10 需大面积改写（含 `StdRng` 不可 Clone 的结构性调整），且 0.10 带 `WeightedIndex` / `Uniform` 行为修复，会引入与旧仓的采样口径偏差，不利于固定种子对照。
- **补充：0.10 的 `StdRng` 无 Clone 等价物**
  - 成因：`StdRng` 底层由 `rand_chacha` 换成 RustCrypto 的 `chacha20` 类型，该类型不实现 `Clone`；rand 对 CSPRNG 也采取「不给 Clone，避免密钥流重复」的立场。仅 `StdRng` 受影响，`Xoshiro*` / `SmallRng` / `ThreadRng` 在 0.10 仍可 Clone。
  - 替代方案均非「克隆当前状态」：`SeedableRng::fork()` 是从当前 RNG 派生新子流且**会推进父流**；`from_seed` / `seed_from_u64` 需自留 seed 才能重建；或换用可 Clone 的 PRNG（数值会变）。
  - 影响面：旧仓把 `rng.clone()` 当「peek 不消耗」与「给子任务独立流」两种惯用法，散落上百处（含 `rng.clone().next_u64()` 探针、`RolloutSeeds::from_rng(&mut rng.clone())`、`eval_rng = rng.clone()`），无一对一替换。
  - 长期方向（若将来升级）：把上述惯用法迁到可 Copy 的自有 RNG（`SplitmixRng`）或 `Xoshiro256PlusPlus`；顺带摆脱 `StdRng` 不保证跨版本可复现的隐患。
- **状态**：已处理（正式更新文档时再补充细节）。
