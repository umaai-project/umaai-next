# 问题记录

记载复杂问题的解决过程与根因，避免重复踩坑。

体例：**已解决**条目只留「坑（现象 / 诱因）+ 结论（处置与口径）」速查，排查过程随问题闭环删除；**未闭环**条目（如事件成功失败口径）保留完整背景、现状与待调整项。

## 2026-10-17

### 呈现宽度必须收口到「写行」这一处

- **坑**：宽度只喂给了面板与表格，过程行原样写出——40 至 69 列终端整屏溢出（探测下限是 40，落在这区间必现）；显式 `--width` 又不走这道下限，过窄时表格把 CJK 切成替换字符。
- **结论**：宽度门禁与折行都收在 `render/term`——折行按显示宽度优先在空格处断、转义序列整段不拆，显式值与探测值同守最小可用列数，入口对低于下限的宽度严格报错；`PrintFrontend` 写行统一走该原语，以后新增行不必各自处理宽度。

### 已装日志器的级别要放共享状态

- **坑**：重复初始化只更新全局门限，已装日志器仍持首次捕获的级别，按配置**提升**级别不生效（调低因门限更紧，看不出来）。
- **结论**：级别放共享状态、`enabled` 每次读取，重装与复用都即时生效；测试断言级别值即可，不必捕获 stderr。

### 冒烟跑不满回合：自选比赛目标未达成是正常终局

- **坑**：默认马娘跑基础局在第 60 回合终止（终局显示 60/77），看着像循环缺陷；实为马娘自选比赛目标场次没跑够时 `next()` 返回 `false`，是「目标未达成＝育成失败」的正常语义。
- **结论**：能否跑满回合取决于**马娘的目标表**而不只取决于引擎；冒烟默认马娘改用目标宽松的一只，夹具与默认层保持同值（`runner_basic` 有断言守门）。要复现早停换回目标苛刻的马娘即可。

### 表格库选型：先分清「库能力不足」与「用法 / 架构问题」

- **坑**：旧仓表格难用（窄终端宽度溢出、想加列就得动游戏逻辑），被当成「库能力不足」，一度考虑换库乃至上 TUI 框架。
- **结论**：宽度溢出是用法错误（库在动态模式下本会读终端宽度，是旧用法硬编码宽度又配百分比列宽）、「加列动逻辑」是架构问题（呈现长在领域类型上，换库治不好），真正的库缺陷只有合并单元格；TUI 是类别错误（全屏界面框架，且与滚动日志 / 重定向不共存）。故选**表格库**、隔离在单一模块（换库只改一处），宽度由调用方显式给出，终端探测另配专职件；**契约 trait 永不加呈现方法**，剧本特化呈现不进本仓。

### 只读 registry 下「包体在缓存里但装不上」

- **坑**：包体已在本地 registry 缓存、索引也能解析，`cargo check` 仍报 `failed to create directory ... Read-only file system (os error 30)`。
- **结论**：cargo 在**构建时**才把包体解包到 registry 的 `src`，`cargo fetch` 只下载不解包，所以「补一次 fetch」无用；换用**已解包可用**的等价件，并把外部接触点收敛到一个函数里。不要搬动 registry 缓存、不要提权。

### 日志门面的装箱安装需要标准库特性

- **坑**：`log::set_boxed_logger` 报「未找到该项」，同文件的 `log::set_max_level` 正常。
- **结论**：该方法由日志门面的 `std` 特性门控；入口层要装箱安装日志器时，把 `log` 的标准库特性登记进 workspace 依赖（本项目全 std，无副作用）。

### 搜索根必须取在决策点

- **坑**：搜索内核的真实 rollout 测试在人头分配处越界 panic（`distribution` 长度为 0）。
- **结论**：初始局面停在回合 0 的 `Begin` 阶段，人头分布要到 `Distribute` 才生成——直接拿初始局面跑训练动作等于在非法搜索根上 rollout；夹具须用真实 `run_stage` 推进到决策点（生产搜索的调用点）再取根，crate 内与跨 crate 端到端夹具同法。

### 桩 rollout 的分数口径必须只依赖动作身份

- **坑**：候选顺序不变性测试失败，同一动作在正序 / 逆序下均分差 6000。
- **结论**：桩分数用「候选下标 × 1000」当基线，逆序后同一动作的下标变了，分数随之改变——是夹具造成的假信号；桩函数改由**动作身份**映射基数，候选下标只用于下标相关断言（如按序取种子）。

### `cargo check` 漏检测试代码

- **坑**：`cargo check -p <crate>` 通过，`cargo test` 编译失败（错误在测试模块内）。
- **结论**：`cargo check` 默认只检查 lib / bin target，不含 `#[cfg(test)]` 与 `tests/`；本地门禁统一用 `cargo check --all-targets` / `cargo clippy --all-targets`（与 CI 一致）。

### lint 门禁在 P4 开工前就是红的

- **坑**：CI 口径的 clippy 失败（29 处告警分布在上一阶段代码里，另有 3 处 rustdoc 链接告警），属提交前未按同一口径自检的历史欠账。
- **结论**：逐条按语义等价修复——整型夹取改 `clamp`；浮点夹取先确认输入不可能是 NaN 再改 `clamp`（`f.min(b).max(a)` 与 `clamp` 在 NaN 上结果不同）；默认值后逐字段赋值改结构体字面量；纯下标循环改迭代器；可合并的嵌套 `if` 改 let-chain；仅「参数过多」一处保留并加 `allow` 与理由（热路径聚结构体会多一层间接）。文档链接按 rustdoc 规则改为可解析目标。
- **口径**：本地门禁与 CI 完全一致——`cargo fmt --all --check` + `cargo clippy --workspace --all-targets -- -D warnings` + `cargo test --workspace --release`，另加 `cargo doc --no-deps` 查链接告警。

### 配置默认值只能有一份

- **坑**：旧仓同一参数在代码 serde 缺省与 `default_config.toml` 各有一套默认值且实测分歧（搜索次数、激进度上限、期望标准差等）；覆盖层用「整段可选结构体」把默认段清空（默认出行顺序被覆盖层空值清成空表）。
- **结论**：默认值**只存在于数据根配置文件**，Rust 侧不为同名字段提供缺省，缺字段即报错并指明字段；覆盖层与默认层同构、字段全可选，段缺失即整段沿用；配置与程序同版本发布，故未知键严格报错（对外帧协议另按宽容口径处理，两者不共用纪律）。

### 真实事件 ID 编码：不能按末位判段

- **坑**：从真机帧还原事件历史时，角色事件被算成「支援卡连续事件第 1 段」。
- **结论**：线上事件 ID 形如 `8 + 归属(5 位) + 序号(3 位)`——归属首位 `3` 为支援卡（值 = 卡 ID）、`0` 为角色 / 友人（值 = 角色 ID），序号是该对象的事件序号。旧实现按 `id % 10` 判段，卡事件序号恰为 1/2/3 时看着没错，但角色事件序号是三位数（如 `809001101` 是角色 9001 的第 101 号事件）。故**先按归属判族、再用三位序号**：卡事件归模拟表的段模板，角色 / 友人事件按真实 ID 入账（模拟表同法编码，ID 天然能对上）。

### 事件成功/失败的建模口径待真实剧本校准

- **背景**：实机事件帧带「成功效果 / 失败效果」两支数值，而模拟事件表**没有「事件成功失败」这一维度**——剧情 / 卡 / 友人事件全是单支必定触发，只有系统事件的比赛结果类带概率。且真实事件 ID 与模拟表 ID 基本不重叠，不存在现成的「真实事件 → 模拟事件」映射。
- **现状（临时口径）**：帧事件按两支重建为待处理事件，两支按常量表的**通用默认成功率**分概率；只有一支带数值时该支必定触发；决策与结算共用同一份数据（同一对象）。事件数值缺失只跳过该事件并留下诊断，不牵连整帧。这一口径会同时影响事件决策的期望值与运气分基线，故不能算最终定论。
- **待调整**：通用默认成功率未必是该事件的真实成功率。等有真实剧本与真机数据后校准，可选方向：按事件类别 / ID 查更细的成功率表；或改成「决策看两支期望、结算以真实结果为准（由下一帧带回）」。调整时只需改事件重建那一处，决策与结算同源这一点不应破坏。
- **边界**：未来事件仍由模拟表 + 概率生成（不可知），只能靠「已发生事件的分族入账」对齐历史，无法消除时机与条件的偏差。

### 合成帧的卡组字段必须带突破等级

- **坑**：会话端到端首次运行即失败，报「校验失败 cardDB.json/3024: 未找到该 ID」。
- **结论**：协议 `cardId` 是「卡 ID × 10 + 突破等级」的合并值，解析侧由支援卡构造拆开取卡面与等级；合成帧的卡组字段一律按合并值写出（旧仓导出方向同法），真机帧本就是合并值、夹具可直接用。

### 阶段不能进契约：通用枚举会把剧本阶段压扁

- **坑**：`Game::stage() -> TurnStage`（6 个通用变体）迫使每个剧本把自有阶段往通用枚举上硬套——拉面一个回合三个决策点、温泉有泡汤，通用枚举没有位置，前端也拿不到剧本真实阶段名。旧仓 `Game` trait 本**没有** `stage()`（阶段完全剧本自持），这处耦合是重建时新引入的。
- **结论（2026-10-17 拍板）**：契约只留**阶段位置标识** `StageId`（剧本显式赋号的数字，引擎只透传、不做分支），剧本内部仍是强类型枚举；`TurnStage` 改名 `BasicStage` 并从底座挪到 `BasicGame` 私有（`BaseGame` 变为纯局面状态，协议层不再写占位阶段）。CRN 阶段键默认取 `StageId`（基础局 0..5 与历史一致，旧种子 / 基线不失效），剧本需要更细粒度可覆盖。
- **两条纪律**：阶段枚举**无数据、无引用、可 Copy**（「吃了哪碗面」一类中间状态在局面字段里）；局面里不存「下一步是什么」，流转只由 `next()` 依数据算出。

## 2026-10-16

### 离线环境下的依赖添加

- **坑**：`cargo add serde_json` 退出 101，报 `rsproxy.cn:443 over proxy 127.0.0.1` 连接失败——该命令需联网更新注册表索引。
- **结论**：加 `--offline` 即走本地缓存完成添加。另注意 `cargo add` **没有 `--workspace` 标志**（会被当作依赖名），登记到 `[workspace.dependencies]` 需按 cargo 解析出的版本手工补一行，再把成员依赖改为 `workspace = true`。

### 核对依赖是否有新版的可行手段

- **坑**：`cargo info <pkg>` 退出 101，报 `crates-io is replaced with non-remote-registry source registry 'rsproxy-sparse'`——该子命令只接受 crates-io 源（需显式 `--registry crates-io` 走直连）。
- **结论**：核对版本改用 `cargo update --dry-run --verbose`——它对「有更新但被版本要求挡住」的包打印 `Unchanged <pkg> vX (available: vY)`；未出现的包即为当前最新。

## 2026-10-15

### rand 依赖版本锚定（0.9.5）

- **坑**：`cargo add rand` 默认解析到 `0.10.3`（破坏性改版：`RngCore` 改名、`StdRng` 移除 `Clone` 等），核心层按 0.9 写法接入后编译失败。
- **结论**：核心层锚定 `rand 0.9.5`（0.9 线最新补丁，与旧仓解析口径一致），配套 `rand_distr 0.5.x`。理由：后续要移植的是基于 0.9 API 的存量代码，且 0.10 带 `WeightedIndex` / `Uniform` 行为修复，会引入与旧仓的采样口径偏差，不利于固定种子对照；升级不是不可行（生态已跟进），只是不划算。
- **0.10 升级障碍（备查）**：`StdRng` 底层由 `rand_chacha` 换成不实现 `Clone` 的 `chacha20`（仅 `StdRng` 受影响，`Xoshiro*` / `SmallRng` 仍可 Clone）；替代手段都不是「克隆当前状态」——`fork()` 会推进父流，`from_seed` 需自留 seed。旧仓把 `rng.clone()` 当「peek 不消耗」与「给子任务独立流」（散落上百处），无一对一替换；长期方向是迁到可 Copy 的自有 RNG 或 `Xoshiro256PlusPlus`。
